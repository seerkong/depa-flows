# Track: add-ai-data-cybernetic-control-protocol

## Problem

AI Data Workflow already owns a durable `RunGraph`, dynamic graph patches, typed Agent tasks and run-local Agent instance identity. What it does not own is a provider-neutral control protocol that lets an AI controller observe that graph, propose the next bounded change, receive rejection feedback and converge without becoming a second graph authority.

Calling a model directly with the raw graph is insufficient. It permits arbitrary code/resource references, leaves port compatibility implicit, makes “complete” indistinguishable from an unverified claim, and encourages each host to invent its own retry counter and patch validation rules.

## Goal

Add reusable contracts and pure Processors for a cybernetic AI Data control step:

`canonical graph + verifier fact + budget -> observation -> controller decision -> admission -> admitted graph patch | typed feedback | terminal outcome`

The controller chooses only from a frozen capability catalog. Admission resolves those choices into the existing `AIDataWorkflowGraphPatch`; applying the patch remains the existing RunGraph owner's responsibility.

## Scope

- Typed goal, observation, verifier, budget, capability-catalog, decision, admission and iteration-receipt contracts.
- A projection Processor that derives a bounded observation from the canonical graph.
- A closed admission Processor that checks observation freshness, budget, protected nodes, capability membership and input/output schema compatibility before producing an existing graph patch.
- Completion admission only after a matching verifier PASS fact.
- Deterministic tests for multiple correction generations, rejected proposals, no-progress limits and reconstruction from canonical facts.

## Out of scope

- Model/provider calls, prompt text and provider-specific retry behavior.
- Eidolon resource loading, Conversation ownership, workflow host lifecycle or public tools.
- A second mutable controller graph, free-form executable code generated by the model, or implicit mutation during validation.
- The final live-model E2E harness; that is implemented by later Mission tracks.

## Success

The public protocol can be used by any host to run an observe/decide/admit loop while tests prove that model-authored data is only a proposal, admitted patches contain only frozen capabilities, invalid decisions do not mutate the graph, and terminal success cannot be asserted without verifier evidence.
