# Design: TaskSpace kernel and local-file authority

## Kernel

TaskSpace is an independent authority with stable space/task/revision identities, a closed task forest, claims, dependencies, lifecycle status, typed profile facts and append-only receipts. Domain profiles extend a closed envelope instead of adding optional fields to kernel tasks.

The exact kernel status union is `Pending | Ready | Claimed | Running | Waiting | Succeeded | Failed | Cancelled`. Dependency satisfaction moves `Pending` to `Ready`; assignment alone does not settle a task. `Succeeded`, `Failed` and `Cancelled` are immutable terminal states. BP terms such as `Delegated`, `Forwarded`, `Refused` and `Abandoned` are BP profile commands/outcomes mapped onto kernel assignment/settlement/cancellation facts; they are not kernel statuses.

A claim is an owner-issued closed fact binding `claimId`, `taskSpaceId`, `taskId`, `assigneeRef`, `attempt`, `leaseEpoch`, `claimedAt`, `heartbeatAt` and `expiresAt`. Only a matching live claim token may enter/continue work or settle. Heartbeat and expiry are explicit Processors; recovery increments attempt/epoch and records the prior expired claim rather than rewriting it. Claim tokens, settlement receipts, replan receipts and history entries use stable idempotency identities. Every receipt and durable command index binds `commandId` to a SHA-256 digest of the complete canonical command; before either owner accepts or replays a raw CAS, it recomputes that digest from the submitted canonical command and requires exact command/envelope/receipt/index agreement. A copied historical digest cannot authenticate a forged body. Task history is append-only owner material; payload/artifact bodies are content-addressed and referenced from tasks/receipts rather than duplicated inline.

All values crossing the kernel/owner boundary belong to one closed own-data domain. It rejects accessors, symbol keys, custom prototypes, sparse or extended arrays, `undefined`, functions, non-finite numbers and cycles without invoking user code. Canonical objects use sorted keys and null prototypes with `defineProperty`, and owner write/read/result boundaries return deep-frozen clones. Terminal classification is a private closed literal predicate rather than exported mutable process state. A referenced artifact is admissible only when an exact digest/size/mediaType body is supplied in the same admission or already exists in the same owner CAS; raw owner CAS enforces the same rule. For an already attached digest, the complete artifact reference, including its optional name policy, must be exact before it may deduplicate; conflicting metadata fails closed.

TaskGroup lifecycle is a kernel projection over child records. `all` and `sequential` succeed only after all children succeed and fail after a child failure/cancellation; `any` succeeds after the first child success and fails only when every child is terminal without success. Group status participates in dependency readiness. Admission and runtime readiness consume one canonical completion graph formed by child-to-parent containment, explicit dependencies, dependencies inherited by group descendants, and ordered previous-sibling edges inside every nested `sequential` group. Validation rejects cycles across that complete graph, including an explicit edge that reverses implicit sequential order.

Processors follow DEPA formulas with explicit runtime: create, patch, claim, heartbeat, start, wait, settle, fail, cancel and replan. The transition owner validates expected revision, forest reachability, dependency rules, claim ownership/lease epoch, history prefix and terminal immutability before calling a store port. Replan may add or revise unrelated nonterminal work, but every surviving terminal task keeps its complete canonical node definition and its incident parent/dependency relations byte-for-byte exact; changing name, description, profile identity/facts, artifacts, order, kind, task identity or an incident relation fails as `terminal-task-immutable`.

## Package boundary

`task-manager-contract` has no effectful runtime implementation; it owns the pure canonical own-data/digest authority required by all adapters. `task-manager-logic` has no Node APIs. `task-manager-file-support` owns only filesystem effects. BP and AI workflow packages own profile codecs/adapters and must not copy kernel transition rules.

## File owner

`task-manager-file-support` accepts an explicit owner root through runtime and has no Flow path in its contracts. The AI Workflow adapter maps that root to `instances/<instance>/runs/<run>/task-spaces/<spaceId>/`; standalone/BP products may select another contained root without changing the durable schema. Each space contains head, immutable records/trees/receipts, history, artifacts and transaction journal. It uses no-symlink real containment, token/pid/inode lock recovery, CAS, file and exact-parent fsync, head-last rename and full digest readback. Every immutable journal entry is fully written and fsynced to a same-directory transaction temp, then atomically published without overwriting an existing final path; an exact final is accepted during roll-forward, a conflicting final fails closed, and the head remains the last durable publication.

Cross-owner settlement is two commits: TaskSpace admits a terminal receipt; FlowRunCheckpoint separately consumes the receipt under its CAS. Repeating either command converges by stable identity. There is no dual write pretending to be one atomic filesystem transaction.

## Compatibility

Existing simple task-manager consumers use explicit conversion helpers. BP TaskStep maps `NotStarted/Active/Delegated/Forwarded/Done/Refused/Abandoned` through a BP profile and retains its business outcome in profile facts while canonical kernel state follows the neutral union. BP TaskGroup aggregation uses the same canonical success classification: `Done`, `Refused` and `Forwarded` are successful handling, while `Abandoned` is not. An `ANY` group returns the exact successful profile outcome with the earliest `endedAtMs` (stable child order breaks timestamp ties), so its BP projection becomes terminal in the same admission as the canonical group; `ALL` and `SEQUENTIAL` wait for canonical terminality before aggregating successful outcomes. New authored/spec and legacy conversions admit only `NotStarted`: a historical non-initial lifecycle requires an explicit event/receipt import protocol and fails closed until that protocol exists. BP profiles carry a monotonic lifecycle sequence so repeated operations such as delegate/reactivate/delegate cannot collide. Codument is deliberately absent from dependencies, tests and durable schemas.
